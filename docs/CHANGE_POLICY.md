# Правила разработки

Документ определяет основные правила разработки проекта JARVIS.

---

## Общие принципы

1. Один коммит — одно логическое изменение.
2. Новые папки создаются только при реальной необходимости.
3. Новые документы создаются только для уже существующего функционала.
4. README и документация обновляются после завершения значимого этапа разработки.
5. Все изменения сначала тестируются, затем попадают в репозиторий.
6. Архитектурные изменения сначала фиксируются в документации, затем реализуются в коде.

---

## Архитектура

1. JARVIS Core должен оставаться независимым от внешних интерфейсов.
2. Все внешние источники данных проходят через **Input Gateway**.
3. Внутренние модули работают только с единым внутренним форматом сообщений.
4. Новые модули должны подключаться без изменения существующей архитектуры.
5. Рабочая архитектура не переписывается без веской причины.

---

## Workflow

1. Каждый workflow хранится отдельным JSON-файлом.
2. Все изменения workflow документируются.
3. Новые узлы добавляются только при необходимости.
4. Названия узлов должны быть понятными и отражать их назначение.

---

## Prompts

1. Каждый системный промпт хранится отдельным Markdown-файлом.
2. Изменения промптов фиксируются в репозитории.
3. Промпты должны быть максимально независимы друг от друга.

---

## База данных

1. Изменения структуры БД оформляются отдельными SQL-файлами.
2. Все изменения должны быть совместимы с существующими данными.
3. Не допускается нарушение целостности долговременной памяти.

---

## Документация

1. Документация должна соответствовать текущему состоянию проекта.
2. Не описывается функционал, который ещё не реализован.
3. Все архитектурные изменения отражаются в соответствующих документах.
