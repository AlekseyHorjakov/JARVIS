# Core Principles

Настоящий документ определяет архитектурные принципы, которые являются обязательными для всех компонентов JARVIS.

Изменение любого из этих принципов допускается только при наличии объективной архитектурной необходимости.

---

# 1. Transport Independence

Ядро JARVIS не должно зависеть от способа взаимодействия пользователя с системой.

Любой внешний интерфейс (Telegram, Web, Mobile, Desktop, API и т.д.) обязан проходить через единый Input Gateway, который преобразует входящие данные в унифицированный внутренний объект сообщения.

Ни один внутренний модуль не должен использовать транспортно-зависимые данные напрямую.

---

# 2. Single Source of Truth

Каждая сущность должна иметь одно место, являющееся источником истины.

Не допускается хранение одинаковых правил, описаний или конфигурации в нескольких документах или модулях.

---

# 3. Modular Architecture

Каждый модуль отвечает только за одну область ответственности.

Модули взаимодействуют между собой исключительно через публичные интерфейсы и не должны зависеть от внутренней реализации друг друга.

---

# 4. Memory First

Память является частью ядра системы, а не дополнительной функцией.

Любой модуль, которому требуется пользовательский контекст, должен получать его через единый механизм Memory.

---

# 5. Stateless Skills

Skills не должны хранить собственное состояние.

Все долгосрочные данные сохраняются исключительно через подсистему памяти.

---

# 6. Extensibility

Добавление новых возможностей не должно требовать изменения существующей архитектуры.

Новые функции реализуются путем подключения новых модулей, Skills или интеграций.

---

# 7. Configuration over Code

Все изменяемые параметры должны выноситься в конфигурацию.

Бизнес-логика не должна зависеть от значений, жестко встроенных в код.

---

# 8. Production First

Каждое архитектурное решение должно быть пригодно для дальнейшего промышленного использования.

Временные решения, усложняющие дальнейшее развитие проекта, должны заменяться полноценной реализацией при первой возможности.

---

# 9. Documentation Synchronization

Документация является частью проекта.

При изменении архитектуры, структуры или поведения системы соответствующая документация должна обновляться одновременно с кодом.

:::
